# Runbook: HTTP 403 Forbidden in GitHub Actions scrapers

Scope: `ivannino11/ElFiguerao_fantastats` → workflow `.github/workflows/aggiorna.yml` → step `Scarica i dati` → `scripts/scarica_dati.py` → `apileague.fantacalcio.it`.
The patterns apply to any Python scraper running on GitHub-hosted runners.

Kit contents

| `requirements.txt` | `curl_cffi>=0.13,<1` (needs recent browser profiles) |

## 1. What we know about this API (tested 20 Oct 2026)

Live probes against `onboarding/v1/league/competition/teams` from a cloud (AWS) IP showed three distinct layers, each with its own 403/401 signature:

| Request | Status | `server` | Body | Layer | Meaning |
|---|---|---|---|---|---|
| Plain HTTP client (no browser TLS fingerprint) | 403 | `CloudFront` | HTML `Request blocked … Generated by cloudfront` | AWS CloudFront / WAF | Bot filter: fingerprint or IP reputation |
| Browser fingerprint, no `app_key` | 401 | `Kestrel` | `{"code":"ATH007","message":"Application key is missing"}` | ASP.NET backend | Missing/changed app key |
| Browser fingerprint + `app_key`, missing or invalid token | 403 | `CloudFront` | `{"code":"FAIL","message":"Request failed"}` | Edge auth check | Token rejected |

Consequences:

- The site is behind **AWS CloudFront, not Cloudflare**. The old Cloudflare check in the script (`cf-ray` / "cloudflare") could never fire, which is why your log only said `HTTP 403`.
- A **bad token returns 403, not 401**. So the old "401 = token" branch never caught token problems on this API.
- A cloud datacenter IP with a correct browser fingerprint got past the WAF. That makes "GitHub IPs are blocked" less likely than "the token was rejected". It does not prove it, though: GitHub runners use Azure IPs and the WAF rules can change. The patched script tells the two cases apart from the response itself.

> Most likely cause of the 20 Oct failures (Squadre, Calciatori and Calendario all returned 403): `FANTA_TOKEN` was rejected even though its JWT `exp` is still in the future. For example, a new login on leghe.fantacalcio.it can invalidate older sessions. Confirm this with the A/B test in section 3 before you change anything else.

## 2. Five-minute triage

1. Push the kit (section 8) and run **Actions → Aggiorna dashboard → Run workflow** (`runner=ubuntu-latest`, `diagnose=true`).
2. Open the failed run. Read the `[diag]` lines in `Scarica i dati`, the **Diagnostica download** table in the job summary and the `::error` annotation. Download the `diagnostica-download` artifact if you need the full JSON.
3. Find the `tipo=` value in the table below:

| `tipo` / exit code | Typical signature | Root cause | Fix |
|---|---|---|---|
| `api_403` / **2** | 403, `application/json`, `{"code":"FAIL"}` | Token invalid, revoked or for the wrong account; league permissions | Section 4.1: new token → `gh secret set FANTA_TOKEN` |
| `auth` / **2** | 401, `ATH007` or other code | `app_key` changed, token expired | Update `APP_KEY` in `fanta_utils.py` from the browser's network tab, or renew the token |
| `edge_block` / **3** | 403 HTML, `server: CloudFront` / `x-cache: Error from cloudfront`, or Cloudflare `error code: 1020` | WAF: IP reputation (Azure datacenter), TLS fingerprint, geo | Section 4.6: self-hosted runner → proxy |
| `edge_challenge` / **3** | `x-amzn-waf-action: challenge/captcha`, or `cf-mitigated: challenge`, "Just a moment…" | JS/CAPTCHA challenge | Change IP (self-hosted). Do not try to solve challenges |
| `rate_limit` / **4** | 429, `Retry-After`, Cloudflare `1015` | Too many requests | Section 4.5: wait, then slow down |
| `forbidden` / 1 | 403 without a recognizable signature | Unknown | Send the artifact JSON for analysis |
| network error / 1 | `errore di rete (Timeout…)` | DNS/TLS/proxy down | Re-run; check the proxy |

## 4. Strategies

### 4.1 API authentication tokens

- Get a fresh token: open leghe.fantacalcio.it logged in → F12 → Network → any `apileague` request → `authorization` header → copy the value after `Bearer `.
- Update the secret without the web UI (paste the token when prompted, so it stays out of shell history):
  ```bash
  gh secret set FANTA_TOKEN --repo ivannino11/ElFiguerao_fantastats
  ```
- The script logs `Token valido fino al … (N giorni)` from the JWT `exp`. That date is only an upper bound: the server can revoke the token earlier.
- Avoid logging in again from another device right after updating the secret, if that is what revokes older sessions. Test this once to find out.
- Never print headers. The patched script calls `::add-mask::` on the token and the proxy credentials and redacts any JWT that appears in response bodies.
- `app_key` is the public key of the web frontend. If you get 401 `ATH007`, read the new value from the browser's network tab and update `APP_KEY` in `fanta_utils.py`.
- Generic rule for other scrapers: if an official API exists (GitHub's REST API, for example), use an authenticated token rather than unauthenticated requests. Authenticated limits are much higher and you get explicit `x-ratelimit-*` headers, which the script logs.

### 4.2 User-Agent and fingerprint consistency

- Anti-bot layers compare the **TLS/HTTP2 fingerprint** with the **User-Agent**. The old code sent a hardcoded Chrome/124 Windows UA while retrying with a `chrome119` profile. That mismatch is a strong bot signal.
- The patch removes the hardcoded UA, so [curl_cffi](https://curl-cffi.readthedocs.io/en/latest/quick_start.html) sends the UA that matches the impersonated browser. `impersonate="chrome"` follows the latest Chrome profile in the installed curl_cffi version.
- The profile list is set with `FANTA_IMPERSONATE` (repo variable). Default: `chrome,chrome146,safari184`. Use `FANTA_USER_AGENT` only when you also pin a matching profile.
- The test showed that plain, non-impersonated requests get an HTML 403 from CloudFront. Do not replace curl_cffi with `requests`/`httpx` for this API.
- Keep `origin`, `referer` and `accept-language` as the browser sends them. They are already in `headers_api()`.

### 4.3 Session management

- One `curl_cffi.requests.Session` per identity reuses connections and cookies ([curl_cffi API](https://curl-cffi.readthedocs.io/en/latest/api.html)). That looks like one browser instead of N cold clients.
- Optional warm-up (`FANTA_WARMUP=1`, the default): a GET to `https://leghe.fantacalcio.it/` before the API calls collects edge cookies the way a real visit would.
- Rotation always opens a **fresh session**, with new cookies and a new connection. Edge cookies are tied to the identity that earned them, so carrying them across a profile or IP change is counter-productive.

### 4.4 Retry policy (implemented)

| Class | Retry same identity? | Rotate profile/proxy? | Circuit breaker |
|---|---|---|---|
| `ok` | n/a | no | n/a |
| `auth`, `api_403` | **no** (fail fast) | no | stop all later calls (`auth`) |
| `rate_limit` | yes, honoring `Retry-After` (max 120 s) | no | stop if retries run out (`rate`) |
| `server` (5xx), network | yes, exponential backoff + jitter (max 60 s) | no | no |
| `edge_block`, `edge_challenge`, `forbidden` | no | **yes**, next profile, then next proxy | stop once all combinations fail (`edge`) |

The circuit breaker keeps a dead token or blocked IP from firing dozens of requests (one per matchday lineup). Repeated requests from a blocked IP can lengthen the block.

### 4.5 Rate limiting

- Pacing: 1–2 s of randomized pause between calls (`pausa()`), and `Retry-After` is honored.
- Keep the `concurrency: aggiorna-dashboard` group so manual and scheduled runs never overlap.
- If you enable the `schedule`, keep it weekly or daily, never every few minutes. The data only changes after each matchday is calculated.
- Optional optimization: skip lineups already saved in `data/` for calculated matchdays. This cuts calls from 3 + N to 3 + 1 per run.

### 4.6 IP strategy: CDN/WAF blocks (in order of preference)

GitHub's Ubuntu and Windows runners run in Azure, so they share Azure datacenter IP ranges, published in the `actions` key of `GET https://api.github.com/meta` ([GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). GitHub notes that these runner IPs are dynamically assigned from shared infrastructure, which affects how third-party reputation services rate them ([About GitHub's IP addresses](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-githubs-ip-addresses)). With `FANTA_DIAGNOSE=1`, the script checks its egress IP against those ranges.

1. **Self-hosted runner at home (recommended).** It uses the same residential IP and network as your browser, costs nothing, and its traffic is indistinguishable from your normal use.
   - Repo → Settings → Actions → Runners → New self-hosted runner. Install it on an always-on Linux box (Raspberry Pi, NAS, WSL2 or a small Linux VM). On Windows, the bash heredoc steps need Git Bash on the PATH.
   - Run it manually with `runner=self-hosted`, or set the repo variable `FANTA_RUNNER=self-hosted` for scheduled runs.
   - Security: use it only on this private/personal repo. Never attach a self-hosted runner to a public repo that accepts pull requests from forks.
2. **Single fixed proxy you control.** For example, a tiny HTTP/SOCKS proxy at home exposed via Tailscale/WireGuard, or a cheap VPS outside the big clouds. Store it as the `FANTA_PROXY` secret (`http://user:pass@host:port` or `socks5h://host:port`) and run with `use_proxy=true`, or set `FANTA_USE_PROXY=true`.
3. **GitHub larger runners with a static IP.** These are paid and still Azure datacenter IPs. They only help if the site owner agrees to allow-list the IP.
4. **Rotating proxy pool (last resort).** `FANTA_PROXY` accepts a comma-separated list, and the script rotates through it only after an edge block. Caveats:
   - Your requests are authenticated with your personal token. Requests from many different IPs on one account can look like account sharing and get the token revoked, which makes things worse.
   - Commercial residential pools may violate the site's terms. Use only reputable providers, and only for your own account's data.
   - For an authenticated personal API, a stable IP (options 1–2) beats rotation.

### 4.7 Cloudflare-specific notes (for other scrapers using this template)

- Cloudflare sets `cf-mitigated: challenge` on every challenge-page response ([Cloudflare docs](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/)). The classifier checks it before the status code because challenges can arrive with a 200.
- Responses with `error code: 1020`/`1006`/`1010` and no `cf-mitigated` header are firewall decisions, so there is no challenge to pass ([analysis on DEV](https://dev.to/bshahin/managed-vs-interactive-cloudflare-challenge-how-to-tell-and-why-it-changes-your-fix-3in0)). Change the network (4.6).
- Do not automate CAPTCHA/Turnstile solving. If the challenge is interactive, run the job where a human-equivalent session already exists (self-hosted runner) or ask the site owner for API access.

## 5. Workflow changes (summary)

- `workflow_dispatch` inputs: `runner` (`ubuntu-latest` | `self-hosted`), `use_proxy`, `diagnose`.
- Scheduled runs read the repo variables `FANTA_RUNNER`, `FANTA_USE_PROXY`, `FANTA_DIAGNOSE` and `FANTA_IMPERSONATE`.
- Exit code mapped to a clear `::error` annotation. On failure the `diagnostica-download` artifact is uploaded (7 days). It contains no token and no proxy credentials.
- The diagnostics JSON is written to `$RUNNER_TEMP`, never to `data/`, so the publish step can never commit it.
- Badge, generation and publish steps are unchanged. The job still stops before publishing when the download fails, so you never publish stale or partial data.

## 6. Exit codes

| Code | Meaning | Action |
|---|---|---|
| 0 | All data downloaded | n/a |
| 1 | Partial failure or unknown error | Read the artifact |
| 2 | Auth (`401` or JSON `403`) | Renew `FANTA_TOKEN` (or `APP_KEY`) |
| 3 | Edge block or challenge after all profiles/proxies | Self-hosted runner or proxy |
| 4 | Rate limited | Re-run later; slow down |

## 7. Anti-patterns

- Re-running the same failing job three times in a row. With `api_403` it cannot succeed, and with `edge_block` it can lengthen the block.
- Sending a hardcoded UA that doesn't match the TLS profile.
- Printing request headers or `r.request.headers` in CI logs.
- Committing the token or the proxy URL, even in `dev/` exploration scripts.
- Publishing the dashboard when the download failed (`|| true` on the download step).
- Treating every 403 as "Cloudflare". On this API it is CloudFront, and the most common 403 is the token.

## 8. Rollout

```bash
git checkout -b fix/403-diagnostica
# copy the kit files over the repo (same paths), or:
git apply patch_403.diff
python -m py_compile scripts/scarica_dati.py
git commit -am "scarica_dati: diagnostica 403, sessione, backoff, rotazione profilo/proxy"
git push -u origin fix/403-diagnostica
gh workflow run aggiorna.yml --ref fix/403-diagnostica -f runner=ubuntu-latest -f diagnose=true
gh run watch
```

Merge to `main` once the run's diagnostics confirm the cause. Note that the publish step pushes to `main` even when the workflow runs from the branch.
